RepeaterTastic

An openHop-style host for Meshtastic. A Pi (or any Linux box) runs many virtual Meshtastic nodes in software, all sharing one dumb LoRa modem. Each node gets its own TCP API port that the official apps can connect to, and the nodes route to each other locally.

FeasibleYes, and the radio side needs one small patch.
  • Meshtastic already fits a dumb modem. A packet is a 16-byte plaintext header plus an encrypted protobuf, at most 255 bytes, sent as ordinary explicit-header LoRa. The node logic runs entirely on the ESP32 and uses nothing from the radio chip except the SX126x itself.
  • The MeshCore KISS modem almost works as-is. It already exposes freq/BW/SF/CR, RSSI and SNR per packet, TX-done events, and a channel-busy check. For LongFast (SF11) its preamble is already 16 symbols, the same as Meshtastic's.
  • The one blocker is the sync word. The modem hardcodes RADIOLIB_SX126X_SYNC_WORD_PRIVATE (0x12) at src/helpers/radiolib/CustomSX1262.h:56. Meshtastic uses 0x2B, so right now the modem cannot hear Meshtastic at all. Adding a SetSyncWord sub-command is about 30 lines.
  • Many identities are easier than on MeshCore. Meshtastic addresses are exact 32-bit node numbers, not 1-byte hashes, so working out who a packet is for is a lookup, not trial decryption.

What we take from openHop

openHop Repeater is the renamed pyMC_Repeater, running on openhop_core (the renamed pyMC_core). It is MIT-licensed Python on asyncio. Its virtual companions are the model to copy. Five patterns carry over directly:

  • The host owns the radio. Identities are “bridges” with no radio of their own. They transmit through a single injector (router.inject_packet(origin=…)).
  • One router makes every decision. Every received packet goes through PacketRouter, which hands it to local identities and then to the forwarding engine.
  • One TCP port per identity. Its CompanionFrameServer is an asyncio.start_server per companion, and a new client evicts the old one.
  • Injected packets are tagged with their origin. The originating identity never receives its own packet back, while the other local identities still get it.
  • TX is confirmed by TX-done. KissModemWrapper sends one frame at a time and waits for 0xF8 TxDone. It already matches the MeshCore KISS protocol byte for byte.

Two things to do differently. openHop always transmits a local-to-local message over the air before delivering it in software, which wastes airtime for DMs. Its sync word is also fixed at firmware build time. We make both configurable.

Architecture

One process, asyncio, Python. The rest of this section follows the diagram.

Receive path, in order

  1. Parse and screen the header. Drop from == 0. Ignore next_hop/relay_node when hop_start == 0. Attach RSSI and SNR from the modem's 0xF9 RxMeta.
  2. Check packet history, keyed by (from, id) and shared across the host. A duplicate still counts. It can be an implicit ACK for an identity that is waiting, it can cancel a pending relay, and it can replace a queued copy that has a lower hop limit.
  3. Sniff for routing. Overheard ACKs and replies update the shared next-hop table, because every identity is in the same RF spot.
  4. Decrypt. If channel == 0 and dest is a local node number, use PKI with that identity's X25519 key. Otherwise gather every channel, across all identities, whose 1-byte hash matches. Try AES-CTR on each and accept the first result that decodes as a valid Data protobuf. CTR mode has no MAC, which is also how the firmware does it.
  5. Deliver. A unicast goes to the one identity whose node number matches. A broadcast goes to every identity holding that channel, all at once, which is the “all receive at the same time” requirement.
  6. Relay decision. The relay persona follows the configured role (CLIENT, ROUTER or CLIENT_MUTE). It relays if the packet isn't to or from us, hop_limit is above 0, and next_hop is 0 or our last byte. A relay decrements hop_limit, sets relay_node, and schedules with the SNR-weighted contention window.

Rules that differ from MeshCore

All identities must share the primary channel name and preset

The frequency is djb2(primary channel name) % slots. If one app renames its primary channel, it silently asks for a different frequency. On the client API, reject changes to region, preset, frequency slot and primary channel name, and report the host's LoRa config back unchanged. Secondary channels and PSKs stay per identity.

Node numbers come from the key

From 2.8, node number = crc32(public_key), and a node's first NodeInfo only verifies if that holds. When creating an identity, regenerate the X25519 key until the result isn't reserved (0–3 or 0xFFFFFFFF), has a last byte that isn't 0x00, and has a last byte unique among local identities, ideally among heard neighbours too. verify that ErriezCRC32 is standard IEEE CRC-32.

One relay persona per radio

MeshCore hosts are repeaters by nature. A Meshtastic host with 20 identities that each relayed independently would flood the channel. The persona is an identity too, with its own NodeInfo, and it is what neighbours see as relay_node.

DMs must use PKI

2.7+ rejects channel-key TEXT_MESSAGE DMs addressed to a node (“Rejecting legacy DM”). The virtual node needs X25519 + AES-CCM from day one. When a peer's key is unknown, send a NodeInfo request first.

Reliability belongs to each identity, routing to the host

Retries run per identity: 5 attempts for unicast on 2.8, the last one falling back to flood. Next-hop routes, packet history and airtime are shared.

Airtime is one budget

A 100-byte packet on LongFast takes about 1.0 s. EU_868 allows 10%, which is 360 s an hour for all identities plus relays. Keep a shared hourly budget and priority queues (ACK/routing › reliable › default › background). Stagger periodic NodeInfo, and leave position and telemetry off by default.

Always set Data.bitfield

A 2.8 node treats a packet with hop_start 0 and no bitfield as pre-2.3 firmware and skips it.

Client API servers

Each identity runs its own copy of the firmware's PhoneAPI state machine on its own TCP port. Frames are 0x94 0xC3 ‖ len u16 BE ‖ protobuf, the host receives ToRadio and sends FromRadio, and the maximum frame is 512 bytes.

Must implementCan stub or refuse
  • Two-stage handshake: want_config_id 69420 (my_info, metadata with firmware_version ≥ 2.5.14, channels, config, moduleConfig, complete), then 69421 (own NodeInfo, peers, complete)
  • heartbeat, answered with QueueStatus
  • ToRadio.packet: QueueStatus now, Routing ACK once delivered
  • Admin to self: get/set owner, get/set channel (secondary channels), get config, device metadata, session passkey, begin/commit edit
  • An offline queue replayed on reconnect
  • Region, preset, frequency or primary channel changes: return an error and the host's values
  • XModem/file transfer, OTA, reboot, factory reset
  • Bluetooth, WiFi, display and GPS config (read-only defaults)
  • MQTT client proxy (Links handle MQTT instead)
  • Remote admin of other nodes (later phase)

Discovery. Advertise each identity as _meshtastic._tcp over mDNS with its own port and name, so apps that browse the network see “Base Camp” and “Ops Desk” as separate radios.

Check in phase 0: whether the Android and iOS apps accept a non-4403 port on a manually entered address. If either insists on 4403, give each identity its own IP (extra addresses on the interface, or macvlan in Docker) and bind every server to ip:4403.

Web GUI

The layout copies openHop's dashboard so openHop users feel at home: a sidebar of views, a top bar showing radio health and relay mode, and live data pushed over WebSockets. openHop's UI (openHop_RepeaterUI, MIT, read at acb5162) is built with Vue 3, TypeScript, Vite, Pinia, Tailwind, Chart.js and Leaflet. Its API client is generated from the backend's openapi.yaml. RepeaterTastic uses the same stack and the same codegen step.

Backend for the GUI

  • Web server: FastAPI on uvicorn, in the same asyncio loop as the router, so the UI reads live state directly with no IPC. openHop runs CherryPy in a thread. FastAPI generates the OpenAPI spec itself, which feeds the UI's api:generate step exactly as openHop's spec does.
  • Auth: the setup wizard creates the admin account. Browser sessions use JWT; scripts and Home Assistant use API tokens. Default bind is 0.0.0.0:8080.
  • Official Meshtastic web client: each identity also serves the firmware's HTTP API, PUT /api/v1/toradio and GET /api/v1/fromradio (src/mesh/http/ContentHandler.cpp). That means the official Meshtastic Web client can open any identity, which gives a second full-featured client for little extra work.

Phases

Each phase ends with something testable against real Meshtastic hardware, and the order is forced: nothing later works without the one before.

  1. 0

    Proof of air

    • Patch the KISS modem (sync word, preamble), flash a Heltec V3.
    • A throwaway Python script: sniff LongFast, decode headers, decrypt the default channel, print text.
    • Hand-build and transmit one broadcast text. Check the app port question from the Client API section.
    Exit: a stock Meshtastic phone shows our text on LongFast, and we show theirs.
  2. 1

    Wire library

    • Header codec, channel hash, key expansion, AES-CTR, PKI CCM, djb2 frequency slots, region and preset tables, LoRa airtime maths.
    • Protobufs generated from meshtastic/protobufs, pinned to a tag.
    • Golden vectors captured from meshtasticd (native) with known keys.
    Exit: bytes match meshtasticd both ways for every piece above.
  3. 2

    One virtual node, end to end

    • Radio driver (reuse or port openhop_core KissModemWrapper), RX pipeline, packet history, TX scheduler with contention window and channel-busy check, duty-cycle budget.
    • NodeInfo, text, PKI DM with want_ack and retries, ACK/NAK, traceroute replies, relay persona.
    • A FastAPI skeleton with /ws/packets and a bare live-packet page, which becomes the debugging tool for every later phase.
    Exit: the virtual node appears with its key in a stock node's list, and DMs show delivered ticks in both directions.
  4. 3

    Client API

    • TCP server, PhoneAPI state machine, admin-to-self subset, mDNS advertisement.
    • Test order: Python TCPInterface, then Android, then iOS.
    • Browser chat over /ws/identities/{node}/api, plus the per-identity HTTP API so the official Meshtastic Web client can connect.
    Exit: the official apps connect, list nodes, and send and receive channel messages and DMs through the virtual node.
  5. 4

    Many identities

    • Identity manager with hot add and remove, key generation under the last-byte rules, a port or IP per identity.
    • Local short-circuit, shared next-hop table, staggered periodic traffic, SQLite persistence (keys, NodeDB, channels, outbox).
    • GUI: setup wizard, Identities, and Nodes & map, with JWT login.
    Exit: 20 identities connected at once, all receive the same broadcast, local DMs work with the RF link unplugged, 48-hour soak on a live mesh with no duplicate relays.
  6. 5

    Links

    • UDP multicast interface, host-to-host link, MQTT gateway, per-link channel filters.
    Exit: a message from RF at site A reaches a meshtasticd node on the LAN and an app on site B's host, then comes back.
  7. 6

    Operate it

    • YAML config with live reload. The rest of the GUI: dashboard charts, statistics, packet archive with byte-level detail, channels with QR import/export, links, configuration, backup and restore, logs, API tokens.
    • systemd unit, Docker image, Prometheus metrics.
    • 2.8 XEdDSA signing on by default, AEAD channels once they ship in a tagged release, remote admin.
    Exit: someone else installs it on a Pi from the docs alone.

Testing

  • Reference peer without RF. meshtasticd native in Docker with UDP multicast enabled. Point RepeaterTastic's udp_sim radio at the same group and the whole stack, including routing, runs in CI against real firmware logic.
  • Golden vectors. Give meshtasticd fixed keys and capture every packet type. Unit tests must reproduce the bytes exactly.
  • Bench RF. Two Heltec V3s, one on stock Meshtastic and one on the KISS modem, with attenuators or dummy loads. Script scenarios with the Python API on the stock node.
  • Apps. A manual checklist per release for Android and iOS: connect, handshake, DM with ticks, channel message, rename, add a secondary channel, reconnect replay.
  • Live soak. 48 hours on the local mesh, watching duplicate relays, airtime percentage, ACK success rate and RX drops while TXing.
  • Later, optional. Your virtual-sx1262 already emulates the chip RadioLib drives. Meshtastic firmware also drives SX1262 through RadioLib, so a MeshBench-style RF-accurate multi-node test could host it too. Not needed to ship.

Risks

USB serial round-trip jitter blurs the ~28 ms contention slotsMediumMeasure in phase 2. If it hurts, add a TxAfter(ms) sub-command so the modem owns the final delay and the channel-busy check. The SPI path avoids this entirely.
Apps can't address several nodes on one IPMediumAn IP per identity (aliases or macvlan), plus mDNS. Settled in phase 0.
Protocol churn: node numbers from keys, signing and retry counts in 2.8, AEAD on masterMediumPin a protobufs tag, keep a compatibility matrix per firmware minor version, and run the meshtasticd CI peer at two versions.

GUI scope creep: openHop's views alone are ~19k linesMediumShip views in phase order, packet feed first. Everything goes through the REST API, so scripts and Home Assistant work before the UI is finished.

Decisions for you

Standalone project or part of openHop?

Recommend standalone, in Python, importing openhop_core.hardware for the radio drivers. The protocols share nothing above the radio, and one modem can't serve both networks at once (different sync word and frequency). A host could still run openHop and RepeaterTastic side by side with two modems, and a shared web UI can come later.

Should the host relay?

Recommend configurable, defaulting to client. Use router only for a well-sited box, and mute for indoor Pis that only host identities.

Local DMs: software only, or over the air too?

Recommend software only. It saves airtime and still works when the radio is unplugged.

Fork openHop's UI or build a new one?

Recommend a new app on the same stack and layout, reusing openHop's generic components under their MIT notice. A straight fork would mean carrying and deleting thousands of lines of MeshCore views. Keep the look close enough that someone running both feels at home.

Upstream the modem patch to MeshCore?

Recommend yes. It's generic (sync word and preamble), it helps openHop, and it avoids maintaining a fork of the firmware.

Name

“RepeaterTastic” is a placeholder. The final name should avoid the Meshtastic trademark.
